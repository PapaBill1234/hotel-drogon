**Phase 5 password recovery and step-up (2026-09-26).** This unit was a **decision gate** and the user chose the path: legacy `forgot.php` recovered a password by emailing a newly generated one, but this project has **no mail transport at all** — `HoloMail` called PHP's host-daemon `mail()`, and there is no SMTP client, no Mailpit/MailHog and no mail setting anywhere — while the plan asks for "password reset tokens … with their own token, expiry, and failure tests", which legacy had no equivalent of. Work stopped, one question was asked, and the answer was **token-based reset with delivery behind a logged interface**. What shipped:

- **Both legacy `actionForgot` and `actionList` are ported.** Password recovery requires username **and** email to match exactly with `mail_verified = '1'` — legacy's own predicate, condition for condition. Username recovery takes the address alone and lists the names on it, as legacy did (it did not require verification for that action either).
- **The token is single-use and expires server-side.** It is generated with the session token generator, stored in Redis **only as a SHA-256 hash** under `password_reset:<hash>` with a 30-minute TTL, and consumed with `GETDEL` — one atomic step, so exactly one of two racing requests can see it. No PolarIS column was added, because PolarIS has none for this and rule 1 forbids adding one for convenience.
- **Delivery is behind `MailService`, whose only transport logs.** It records recipient and subject and withholds the body — a reset body carries a live token, which must not reach log storage. It reports `logged`, never `delivered`, and `tests/unit/MailServiceTest.cpp` asserts exactly that, plus that a recipient-less message fails rather than silently succeeding. An SMTP transport is a dependency decision under plan rule 9, not yet taken.
- **`reauthenticate.php` and its flag are ported.** `reauth_required` lives in the Redis session document (server state, not a client claim), `/api/account/session` reports it, and `/client` refuses and routes to the step-up screen — the check `client.php` performed before anything else on the page ran. Clearing it re-runs the full credential check through the same service method login uses.
- **Anonymous CSRF is a real control, not an exemption.** The three recovery routes carry a new `CsrfPublicFilter` instead of `CsrfFilter`: they exist for a caller with no session, and `CsrfFilter` validates against a session-bound token that cannot exist yet. The substitute requires the `X-XSRF-TOKEN` **header**, which a cross-origin request cannot set without a CORS preflight this application does not answer. It checks presence, **not value** — there is nothing to compare against before a session exists — and says so in its own header so a future reader does not mistake it for token validation. `check_csrf_rules.py` gained an explicit `PUBLIC_CSRF_ROUTES` list that still fails the build if a listed route drops the filter.

**Three defects were found and fixed rather than worked around**, two of them only visible end-to-end:

1. **`getUserSession` never parsed `reauth_required` back.** The writer stored it and the reader silently dropped it, so `/api/account/session` reported `false` forever. Redis demonstrably held the flag while the API denied it; that contradiction is what located it.
2. **The anonymous client could never send the CSRF header.** `requestJson` reads the `XSRF-TOKEN` cookie and omits the header when there is none — which is every pre-session caller — so all three recovery routes returned 403 from the browser while passing when driven by a script that set the header by hand. A named `PUBLIC_CSRF_MARKER` now supplies the literal for routes that check presence only.
3. **The header's forgot-password link was a bare `<a>`**, forcing a full document load into a client-side route. It is a router `Link` now; the rendered href is unchanged, which the parity run confirms.

**Divergences from legacy, deliberate and recorded:** the password form answers with **one** message for every outcome instead of legacy's distinct "Invalid details.", which turned it into an oracle for which accounts exist; and the reset flow mails a single-use **link** rather than a plaintext password, which is what the plan asked for.

**Phase 5 remember-me (2026-09-26).** The last piece of the legacy session model, read from the checkout before writing anything:

- **Issue.** `classes.php` generated `GenerateTicket("remember")` — `random(6) . "-" . bin2hex(random_bytes(10)) . "-" . bin2hex(random_bytes(10))`, 48 characters — stored **only its SHA-256 digest** in `users.remember_token_hash` (`varchar(64)`, exactly one digest) with the expiry in `users.remember_token_expires_at`, and set two cookies whose names are kept verbatim: `rememberme` = "true" and `rememberme_token` = the raw token. Both columns are PolarIS's own; nothing was added or widened. The lifetime comes from `site_cookie_time`, which the installer seeded to **14 days**, so that is the documented fallback for a missing or unparseable value.
- **Consume.** `security_check.php?type=token` was reached through `core.php`'s front-controller condition — anonymous **and** `$_COOKIE['rememberme'] == "true"` — then looked the user up by digest with `remember_token_expires_at > time()`, refused a banned account, logged them in, and **set `$_SESSION['reauthenticate']`**. That last step is the point: a token restored the session but never granted entry to the hotel. `/api/auth/remember-login` reproduces all of it, including the two-cookie precondition, and clears the digest so a token is spent after one use.
- **The flag now arises in normal use.** This closes the gap the previous unit recorded: `reauth_required` was reachable only from a seeded test, and remember-me is what sets it. `AccountPage` renders the step-up screen in place when the flag is set, so the visitor keeps the URL they asked for and gets the page once the password is proved — the destination `reauthenticate.php` restored from `$_SESSION['page']`.
- **Signing out ends the credential.** `logout` now clears the stored digest and all four cookies. Legacy cleared only the cookies; leaving the digest live would mean a copied value still worked after the user had deliberately signed out — a session the user cannot end.

**Two defects were found and fixed rather than worked around**, both by tests rather than by reading:

## Known gaps opened or confirmed by this unit

- **A 2% pixel budget is not evidence that a page still has its content.** The `/community` promo had been reading `phpretro_news` instead of `hotelview_news` and rendering five blank slots where legacy renders a story. The page passed visual parity the whole time, because the missing topstory is under 2% of a 1280x800 frame. `visual-parity.spec.ts` now runs a content assertion for that page (DOM crossed against the API payload), which was shown to fail against the pre-fix build. **Other pages still rely on the pixel budget alone** — treat a green parity run as a layout check, not a content check.
- **`#placeholder-container` is `position: static` with zero height on `/community`.** All 18 `.active-habbo-image-placeholder` divs therefore anchor to `#homes-habblet-list-container` and stack at its origin; the 64x110 `habbo_skeleton.gif` spills ~12px below the blue box. Legacy's `fullcontent.js` `ActiveHabbosHabblet.initialize()` assigns each placeholder grid coordinates (3 rows x 6 columns, 62x45 spacing), so with no live data its skeletons stay covered. Fix by porting `_positionPlaceHolderImages` or omitting the placeholders when there is no habbo data. This is a **distinct** defect from the news-table bug and is still open. Found from a user-supplied screenshot, not by the harness.
- **The `collectables` visual baseline compares two different pages.** `docs/reference-screenshots/baseline/collectables.png` shows the **Retro Club** tab active, while the spec captures `/credits/collectables` ("Collectables" active). The diff is ~3% and it fails intermittently. The baseline needs re-capturing against the current legacy capture path before that page's parity means anything. Also note `collectables.php` selects `WHERE time = mktime(0,0,0,date('m'),1,date('Y'))`, and the shared fixture pins `time=1696118400` (2023-10-01), so the page renders its empty state unless the fixture month happens to equal the current month.
- **`docker compose run <service>` does not execute that image's `CMD`.** `frontend-build`'s `CMD` is what copies `/app/dist` into the `frontend_dist` volume, so `docker compose run --rm frontend-build` exits 0, reports success, and leaves nginx serving the **previous** bundle. Use `docker compose build frontend-build && docker compose up -d frontend-build` and then confirm the served `/assets/index-*.js` hash changed. This cost a verification round here: a build that "succeeded" had emitted nothing.
- **There is no mail transport, so nobody receives a reset link.** The flow is complete and tested end to end, but delivery goes to a log. An operator sees "message NOT sent (to=…, subject=…)" and the user gets nothing. Closing this needs an SMTP client or an approved dependency — plan rule 9 — and until then the reset journey must not be described as working for a real user. The response deliberately says only "if those details match a verified account, a reset link has been sent", which is true of the server's behaviour and does not promise an inbox.
- **Nothing sets `reauth_required` yet.** **Closed by this unit** — remember-me sets it, and `AccountPage` enforces it. Kept as the worked example of a gap a later slice was always going to close.
- **The hotel side of the client entry does not exist here.** The website issues the ticket and reports the connection settings, but nothing connects: the legacy client is a Shockwave embed modern browsers cannot run, no client asset exists in this workspace or the legacy fixture, and no PolarIS/Nitro source or emulator is available to verify that a ticket is accepted. `/client` says so on the page rather than pretending.
- **`users.auth_ticket` diverges on an existing database.** The DDL now matches PolarIS (`varchar(256)`, no expiry column), but `CREATE TABLE IF NOT EXISTS` will not alter a database created earlier. The two `ALTER TABLE` statements are in the inventory; they were deliberately **not** run automatically.
- **The transaction ledger has no writer in this stack.** `TransactionService::record` exists and is unit-tested, but nothing calls it: the two legacy callers are the housekeeping credit adjustment (Phase 9) and the MyHabbo Homes store (Phase 8). `/credits/history` is correctly empty on any stack the new code alone produced — do not "fix" it by inventing rows.
- **No login throttling.** `UserAccountService::authenticate` has no attempt counter, lockout or backoff. This matters more with every credential route added: the recovery routes issue a token per matching request, and remember-me issues a 14-day credential per login, none of them rate-limited.
- **The signed-in pages are verified functionally, not visually.** No screenshot baseline exists for any signed-in page. The legacy class names and ids are reused so the legacy stylesheets apply, but that is a design intent, not a measurement.
- **Hashed asset bundles accumulate in the `frontend_dist` volume.** The build service copies into the volume rather than replacing it, so each distinct hash stays. Harmless today, but the volume grows with every distinct build, and hashed assets are served with no `Cache-Control`.

**Community promo fix (2026-09-26).** A user compared `http://localhost:3000/community` with `http://localhost:8081/community` and reported they "dont really look the same". They were right, and the cause was a data-source error rather than a styling one:

- **Two legacy news tables.** `community.php:372` reads `hotelview_news` (`ORDER BY id DESC LIMIT 5`); `articles.php:17` reads `phpretro_news` by id. The React page fed the promo from `/api/public/news` (`phpretro_news`), so it showed the wrong articles, and once that list was shorter than five it padded blank filler slots — rendering an empty blue box where legacy shows a story.
- **Ported, not invented.** `hotelview_news` now exists with the column shapes copied from the legacy schema dump, seeded with the ship row that dump contains, and is served by `GET /api/public/community-news`. The page shapes rows exactly as the PHP did: `nl2br($input->HoloText($text))` for the summary, `HoloText` for the title, `HoloUrl` for the sprite, and `stringToURL($title, true, true)` for the permalink slug. The `button_*` columns are selected by the legacy query but never rendered, so they are not in the API.
- **Why the harness had missed it.** The committed baseline already showed `Open Your Summer Calendar!`, so the comparison was measuring correctly — the missing paragraph is simply smaller than the 2% budget of a 1280x800 frame. `visual-parity.spec.ts` now cross-checks the rendered promo against the API payload for that page, and that assertion was shown to fail on the pre-fix behaviour before being kept.
- **Verification.** Endpoint returns the legacy row verbatim; `visual-parity.spec.ts` **6/6** in the pinned `mcr.microsoft.com/playwright:v1.63.0-noble` image with `site_closed=1` (the maintenance baseline's precondition), community green on its own afterwards with the site open; Phase 4 public smoke **21/21** (was 17/17, four new assertions); `check_polaris_access.py`, `check_csrf_rules.py` (58 routes / 30 mutating), `check_admin_ui_coverage.py` all green; Catch2 **143 assertions in 8 cases**; backend and frontend images build clean; `check_dependency_pins.py` fails on pre-existing archive drift (unrelated — pinned packages moved in the Ubuntu archive).
- **Left open, with evidence.** The "Random Habbos" skeleton sprite that also appears in the user's screenshot is a **separate** defect (placeholders unpositioned because `#placeholder-container` has zero height) and is recorded above rather than silently folded into this unit. The `collectables` baseline misalignment is likewise recorded, not fixed.
