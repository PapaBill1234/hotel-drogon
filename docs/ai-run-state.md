## Known gaps opened or confirmed by this unit

- **No login throttling.** `UserAccountService::authenticate` has no attempt counter, lockout or backoff, so repeated wrong passwords cost the server the same as correct ones. The contract's own description says which statuses represent what; it says nothing protective. Recorded in the inventory; not introduced by this unit and not fixed by it.
- **The account pages are verified functionally, not visually.** No screenshot baseline exists for any signed-in page (all six baselines are anonymous public pages), so "matches legacy" is not claimed for `/me` or `/account/profile`. The legacy class names and ids are reused so `v2/styles/personal.css` applies, but that is a design intent, not a measurement.
- **Hashed asset bundles accumulate in the `frontend_dist` volume.** The build service copies into the volume rather than replacing its contents, so each distinct bundle hash stays. Harmless today (nginx resolves `index.html` per request, and the shell itself is not served with a long cache header), but the volume grows with every distinct build. Notes for whoever picks this up: hashed assets are also served with **no** `Cache-Control`, so the immutability that content hashing is for is not actually exploited.
- **`/me` and `/account/profile` are not in any screenshot pipeline**, so a future visual regression there would be silent.
