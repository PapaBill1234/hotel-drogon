**Login throttling at the shared credential boundary, and the defect it uncovered (2026-09-28, gap 2 of the three).** `src/services/LoginThrottle.cpp` counts consecutive credential failures in Redis and `UserAccountService::authenticate` calls it *before* the account lookup, so a throttled caller costs one Redis read and reaches neither MariaDB nor the password comparison. Two counters, because they stop different attacks: **5** failures per account name and **20** per client address, in a **900 s** window that each failure refreshes (`INCR` then an unconditional `EXPIRE`, so a counter cannot be waited out mid-attack). A successful sign-in `DEL`s the account counter; the address counter deliberately survives it, or an attacker with one working account could reset their own spray budget. Past a limit the answer is `errorCode` 5 — **429** with a `Retry-After` header and one constant message for both limits — and all four callers map it, because "Current password does not match" would be a claim about a password that was never compared. Redis being unreachable is a refusal, not an open door: with the counter store down, a wrong password would still answer 401 while a right one failed later in the session layer with a different error, which is exactly the oracle throttling exists to remove.

* **The live check found the defect, and it was not the one being looked for.** `scripts/check_login_throttle.sh` prints the counter key it seeds, and it read **`login_fail:a:172.27.0.5`** — the nginx container's address. `req->peerAddr().toIp()` is the proxy for every request, because the backend has no published port and every visitor arrives through nginx. The address budget would therefore have been **one budget for the whole site**: twenty failed sign-ins from anybody would have refused sign-in for everybody for fifteen minutes, and every counter would have looked healthy while it happened. Fixed by `utils::ClientAddress`, which prefers `X-Real-IP` when it is a plausible literal — `proxy/nginx.conf` sets it to `$remote_addr` on every API location, overwriting whatever a client sent — and falls back to the peer otherwise. **Two backend defects were found by this unit's own verification, and both were real.**

1. **A lock-upgrade deadlock in the version compare-and-swap.** The transaction used to open with `INSERT IGNORE INTO phpretro_myhabbo_homes …` to create a missing version row; InnoDB's duplicate-key check takes a **shared** lock on the existing row, and both concurrent saves then tried to upgrade it for the `UPDATE`. Measured by `smoke_phase8_homes.sh` section 7: `A=200 B=503`, MariaDB **1213**. The insert now runs before the transaction opens, where it autocommits and holds nothing; the CAS is the transaction's first statement, which is what the design always claimed. Re-measured afterwards with the same two-request race: **A=200 (0.036 s), B=409 (0.007 s)**.
2. **An aborted save could leave its row locks held forever.** Drogon's `Transaction` commits when its last `shared_ptr` dies *unless its own `rollback()` has completed*, and `rollback()` only sets that guard from its completion callback. Calling `rollback()` and then dropping the reference therefore races the guard: the destructor queues a COMMIT and — the part that bites — installs its own connection idle callback, replacing the one the transaction uses to drain its queue. The queued ROLLBACK was never dispatched, the transaction stayed open, and every later save blocked on the version row: the smoke suite hung with **no request reaching the application again**, and the next run hung on its first save. The abort now sends `ROLLBACK` as the next statement in the chain the transaction is already driving, so the queue drains in order and the destructor's COMMIT lands after the database has already ended the transaction, where it is a no-op. The reasoning and the failure it caused are in the code at `TxnSteps::abort`.

**The concurrency control is the point of this unit, and it is two independent mechanisms.** The plan's exit condition is "concurrent edits don't silently overwrite each other", so the unit was designed around proving it rather than around the endpoints:

1. **A Redis edit lock** per home (`SET NX EX 300`, value `<holderId>:<token>`), acquired on opening the editor and required by every write. It is checked before the transaction and is *not* trusted for correctness.
2. **A version compare-and-swap**, as the first statement of the write transaction (`UPDATE … SET version = version + 1 WHERE … AND version = ?`). It takes the row lock, so a second writer blocks there and then finds `affectedRows() == 0`: the transaction rolls back and the caller gets `409` **with the server's current layout in the body**, so the client can roll its optimistic update back without a second request.

Measured: `scripts/smoke_phase8_homes.sh` fires two saves with one version and requires exactly one `200` and one `409`; the loser's placement is absent from the stored layout and — checked in the database afterwards — the loser wrote **no audit row**, which is what proves the rollback rather than a suppressed response.

**Phase 5 SSO replay bound (2026-09-26).** The previous unit ended with a working loopback bridge and one blocker: the pinned emulator consumes a website-issued ticket at game login, restores it during its reconnect grace (`SessionResumeManager.restoreSsoTicket` writes it back into an **empty** column), leaves it on `users.auth_ticket` after a full disconnect, and its game lookup (`HabboManager.loadHabbo`, `SecureLoginEvent`) matches `auth_ticket` **without consulting `auth_ticket_expires_at`**. A ticket read out of browser history therefore opened the account indefinitely. That is emulator behaviour this repository does not own — the pin is `POLARIS_REV=910ed4f6…` and `fetch-upstreams` refuses a dirty checkout — so the bound is enforced by the issuer instead.

**What was measured before any change**, in the lab (`ci-emulator-sso-20260926`, TTL 30 s), using `tests/e2e/sso-replay.spec.ts` as written for the intended bound:

| Path | Pre-fix result |
| --- | --- |
| login | **pass** — the Drogon ticket enters Octane |
| reconnect inside the window | **pass** — the same ticket is accepted again |
| full disconnect | **fail** — `the emulator SSO endpoint still honours the consumed ticket` (200, expected 401) |
| sign-out | **fail** — `the ticket survived the sign-out` (200) |
| past its window | **fail** — `an unused ticket past its window is still honoured` (200) |

A one-line probe confirmed the same fact outside the browser: the 36-character ticket `testuser` used at 15:11 and fully disconnected at 15:11:46 still returned `HTTP 200` with a fresh access token at 15:31.

**The bound that shipped.** A ticket is issued with a deadline, and at that deadline the website replaces it with a *tombstone*:

- `phpretro_sso_tickets` (website-owned, one row per user: ticket, `issued_at`, `void_at`, `voided_at`, `reason`) records the deadline. It is in the **database, not Redis**: a deadline lost to a cache restart would be exactly the unbounded credential this exists to prevent, and `issued_at`/`void_at` are written before `users.auth_ticket`, so a caller never receives a ticket the website has no plan to void.
- `UserAccountService::voidExpiredAuthTickets` runs on a 5 s Drogon timer (bounded batches of 25, oldest first) and calls `voidIssuedAuthTicket`, which writes a tombstone with
  `UPDATE users SET auth_ticket = ? WHERE id = ? AND (auth_ticket = ? OR auth_ticket = '')`.
  The `auth_ticket = ''` arm is the point: voiding the *empty* column is what stops the emulator's grace-period restore writing the dead ticket back. A ticket rotated in the meantime, or one another issuer wrote, is left alone.
- The tombstone is `void-` + 190 random hex characters (`Crypto::generateVoidSsoTicket`): **longer than the 128 characters both PolarIS doors accept as a presented ticket** (`SecureLoginEvent` disposes the connection, `SessionEndpoints.handleSsoToken` answers 400), and inside `auth_ticket varchar(256)`. A leaked tombstone is not a credential; an empty column would have been a resurrection.
- Sign-out voids the caller's ticket immediately, in the same `logout` chain that clears the remember-me digest.
- `/api/account/client-entry` reports `sso_ticket_void_at`, the page states the time, and `SSO_TICKET_TTL_SECONDS` (default 120, clamped 5–3600) is the window operator knob.

**Phase 5 password recovery and step-up (2026-09-26).** This unit was a **decision gate** and the user chose the path: legacy `forgot.php` recovered a password by emailing a newly generated one, but this project has **no mail transport at all** — `HoloMail` called PHP's host-daemon `mail()`, and there is no SMTP client, no Mailpit/MailHog and no mail setting anywhere — while the plan asks for "password reset tokens … with their own token, expiry, and failure tests", which legacy had no equivalent of. Work stopped, one question was asked, and the answer was **token-based reset with delivery behind a logged interface**. What shipped:

- **Both legacy `actionForgot` and `actionList` are ported.** Password recovery requires username **and** email to match exactly with `mail_verified = '1'` — legacy's own predicate, condition for condition. Username recovery takes the address alone and lists the names on it, as legacy did (it did not require verification for that action either).
- **The token is single-use and expires server-side.** It is generated with the session token generator, stored in Redis **only as a SHA-256 hash** under `password_reset:<hash>` with a 30-minute TTL, and consumed with `GETDEL` — one atomic step, so exactly one of two racing requests can see it. - **Delivery is behind `MailService`, whose only transport logs.** It records recipient and subject and withholds the body — a reset body carries a live token, which must not reach log storage. It reports `logged`, never `delivered`, and `tests/unit/MailServiceTest.cpp` asserts exactly that, plus that a recipient-less message fails rather than silently succeeding. An SMTP transport is a dependency decision under plan rule 9, not yet taken.
- **`reauthenticate.php` and its flag are ported.** `reauth_required` lives in the Redis session document (server state, not a client claim), `/api/account/session` reports it, and `/client` refuses and routes to the step-up screen — the check `client.php` performed before anything else on the page ran. Clearing it re-runs the full credential check through the same service method login uses.
- **Anonymous CSRF is a real control, not an exemption.** The three recovery routes carry a new `CsrfPublicFilter` instead of `CsrfFilter`: they exist for a caller with no session, and `CsrfFilter` validates against a session-bound token that cannot exist yet. The substitute requires the `X-XSRF-TOKEN` **header**, which a cross-origin request cannot set without a CORS preflight this application does not answer. It checks presence, **not value** — there is nothing to compare against before a session exists — and says so in its own header so a future reader does not mistake it for token validation. `check_csrf_rules.py` gained an explicit `PUBLIC_CSRF_ROUTES` list that still fails the build if a listed route drops the filter.

**Three defects were found and fixed rather than worked around**, two of them only visible end-to-end:
