**Phase 5 credits slice (2026-09-26).** `/credits` and `/credits/history` now serve React, from `credits.php` and `history.php`. Two things had to be read before either could be written:

- **Wallet vs ledger.** `credits.php`'s purse read `$user->user("credits")` — the live PolarIS row — and did **not** touch the ledger. So `/api/account/purse` reads the row too. Deriving a balance by summing `phpretro_transactions` would have disagreed with the hotel the moment the emulator changed credits itself, and would have been a silently different number from the one the legacy page showed.
- **The ledger's writers.** `phpretro_transactions` is written by exactly two legacy paths: `housekeeping/users.php` (type `admin_grant`, amount = new − old credits, description `Housekeeping credit adjustment`, reference_id = the user id) and `includes/PhpretroHomes.php` (type `homes_store`, amount = −price, description `MyHabbo store: <item>`, reference_id = the catalogue id). `history.php` reads `created_at DESC, id DESC LIMIT 100`. All of that is ported verbatim into `TransactionService`, whose table is created from `migrations/001_custom_tables.sql` — column for column, including `reference_id` NULL and the `idx_user_id_created` index name, because the legacy writers still insert into this table.

**Neither writer is ported yet** (Phase 9 and Phase 8 respectively), so a normal stack has an empty ledger and the page correctly shows `history.php`'s own empty-state sentence. That is parity with a fresh legacy install, not a stubbed success — and the browser suite proves the populated path by installing two rows in exactly the legacy shapes, asserting the ordering (`created_at DESC` beats insertion order), the negative amount, the `Y-m-d H:i` format and the empty state, then removing them again in a `finally`.

## Known gaps opened or confirmed by this unit

- **The transaction ledger has no writer in this stack.** `TransactionService::record` exists and is unit-tested, but nothing calls it: the two legacy callers are the housekeeping credit adjustment (Phase 9) and the MyHabbo Homes store (Phase 8). Until one of those lands, `/credits/history` is correctly empty on any stack the new code alone produced. Do not read the empty state as a defect, and do not "fix" it by inventing rows.
- **No login throttling.** `UserAccountService::authenticate` has no attempt counter, lockout or backoff, so repeated wrong passwords cost the server the same as correct ones. Recorded in the inventory; not introduced by this unit and not fixed by it.
- **The account and credits pages are verified functionally, not visually.** No screenshot baseline exists for any signed-in page (all six baselines are anonymous public pages), so "matches legacy" is not claimed for `/me`, `/account/profile`, `/credits` or `/credits/history`. The legacy class names and ids are reused so the legacy stylesheets apply, but that is a design intent, not a measurement.
- **Hashed asset bundles accumulate in the `frontend_dist` volume.** The build service copies into the volume rather than replacing its contents, so each distinct bundle hash stays. Harmless today (nginx resolves `index.html` per request, and the shell itself is not served with a long cache header), but the volume grows with every distinct build. Hashed assets are also served with **no** `Cache-Control`, so the immutability that content hashing is for is not actually exploited.
- **Signed-in pages are not in any screenshot pipeline**, so a future visual regression on `/me`, `/account/profile`, `/credits` or `/credits/history` would be silent.
