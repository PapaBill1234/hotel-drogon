# Current parity and release-gap inventory

Updated 2026-09-28 for the Phase 8 Homes Store browse API and modular-CMS work, with the latest local evidence below. This file tracks the Drogon/React application. The former 50 KB inventory, including the Laravel attempt and the investigation diary, is preserved verbatim in [the v1 archive](archive/phase1-parity-inventory-v1.md) and in Git history. The [stable plan](cpp-drogon-conversion-plan.md) owns architecture and safety rules; [run state](ai-run-state.md) owns the active unit.

**Status terms:** *Verified* means the cited check passed for its stated scope; *implemented* means code exists without the complete user journey; *gap* means no working current-stack path; *decision gate* means the named approval or emulator evidence is required. A passing phase exit does not imply release readiness.

### SSO ticket lifetime carried by this unit

The pinned emulator is not the place this project can fix the ticket lifetime: `POLARIS_REV` is pinned, `fetch-upstreams` refuses a dirty checkout, and its game login deliberately matches `users.auth_ticket` without consulting `auth_ticket_expires_at` (its own comment records that a stale expiry used to block third-party CMSes that write only that column). So the issuer bounds the credential:

- `phpretro_sso_tickets` (website-owned, one row per user) holds the ticket, `issued_at`, `void_at` and `voided_at`. It is **not** in Redis: a deadline lost to a cache restart would be exactly the unbounded credential this prevents.
- At the deadline a 5 s sweep writes a tombstone with `auth_ticket = ? WHERE id = ? AND (auth_ticket = ? OR auth_ticket = '')`. The `= ''` arm reaches the state a consumed ticket leaves behind, which is the state the emulator's grace-period restore writes back into — clearing to empty would hand the dead ticket straight back to whoever holds the URL.
- The tombstone (`void-` + 190 hex) is longer than the 128 characters both PolarIS doors accept as a *presented* ticket, so it is not a credential even if it leaks.
- `SSO_TICKET_TTL_SECONDS` (default 120, clamped 5–3600) and `SSO_TICKET_SWEEP_SECONDS` (default 5) are the operator knobs. The window must exceed a client launch; the lab overlay uses 90 s and the CI stack 10 s so the void can be observed inside a job.

**A pre-existing crash on this route was found and fixed.** Ten consecutive `POST /api/account/client-entry` calls killed the backend with the `Exited (139)` signature already recorded in the run state. AddressSanitizer named the fault: the four parallel `phpretro_site_settings` lookups complete on different database loop threads, and their shared `std::map` and `remaining` counter were unsynchronized — two callbacks inserted into one map at once (tree corruption, SIGSEGV), and the counter's race could answer a request twice or never. Both are now guarded by a mutex, with the last callback copying the values out under the lock. Measured: before, a 100-request loop killed the release build at request 8 and the ASan build at request 10; after, 100/100 release and 120/120 ASan, both healthy. CI asserts the bound on the row in every integration run (`scripts/check_sso_replay_bound.sh`), and all three jobs passed in [run 36258890816](https://github.com/PapaBill1234/hotel-drogon/actions/runs/36258890816) on the branch and again in [run 36265374430](https://github.com/PapaBill1234/hotel-drogon/actions/runs/36265374430) on `main`, which the branch was merged into (fast-forward to `ac006ff`; PR [#1](https://github.com/PapaBill1234/hotel-drogon/pull/1) closed as merged). The first of those runs existed only because the conflicted pull request was merged up first — a conflicted pull request gets no workflow runs at all.

### Schema correction carried by this unit

`users.auth_ticket` was declared `VARCHAR(255)` in `src/main.cpp`; PolarIS declares `varchar(256)`, and the legacy site wrote a 36-character ticket there. It is now `VARCHAR(256)`. The older CleanDB evidence lacked `auth_ticket_expires_at`, so this repository removed that column from its own initial DDL and ticket writer. The newly pinned PolarIS emulator has verified migrations that **add** `auth_ticket_expires_at` for its own HTTP issuer. Its game SSO lookup ignores the expiry column. It consumes a ticket after successful login, but `SessionResumeManager` restores it during disconnect grace and leaves it present after the grace expires, as observed in the lab. The two schema baselines must not be conflated.

**An existing database may keep its old column shape** — `CREATE TABLE IF NOT EXISTS` does not alter it. After identifying the database owner and installed PolarIS revision, an older website-only schema may need the reviewed width change:

```sql
ALTER TABLE users MODIFY auth_ticket VARCHAR(256) DEFAULT '';
```

No `DROP COLUMN auth_ticket_expires_at` is prescribed for the pinned emulator; it requires that column. No primary database migration was run in this lab work unit.

### Schema additions carried by the Phase 8 widget unit

Two development-schema gaps were found by rendering the page, both the same class as the width change above — `CREATE TABLE IF NOT EXISTS` cannot alter a database that already exists, so an older stack needs the statement run deliberately:

```sql
-- Legacy `PhpretroHomes::profile()` selects `u.last_online`, which is PolarIS's
-- own column (references/schema/CleanDB.sql). Without it the owner read fails
-- with "Unknown column 'u.last_online'" and the home page 404s.
ALTER TABLE users ADD COLUMN last_online BIGINT DEFAULT 0 AFTER last_login;
```

`users_settings` is also created now (columns `guild_id`, `hide_online`, `tags`, `club_expire_timestamp`, typed as CleanDB types them). A stack that predates it needs the `CREATE TABLE` from `HomesService::ensureSchema` run once; `last_online` was added directly to `src/main.cpp`'s `users` DDL and to both development stacks used for verification, which are disposable or local development data. Neither statement touches PolarIS-owned data on a real hotel database: the first adds a column PolarIS already defines, the second is skipped entirely where the table exists.
